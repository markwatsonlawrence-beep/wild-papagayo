## What this project is

Marketing/booking site for **Wild Papagayo**, a private tours, transfers and hotel-experience
company in Guanacaste, Costa Rica (production: https://wildpapagayo.com). It is a **static site
generated by PowerShell scripts** from a JSON knowledge base, plus a small serverless function
for the "Bubu" AI assistant. Content is mostly English; some legal pages have Spanish names
(`politicasdecancelacion`, `politicasdeprivacidad`, `Terminosycondiciones`, `paquete`).

**Positioning:** Wild Papagayo's primary positioning is **private** tours and transportation.
Prefer "private" over "luxury" in copy, titles and metadata unless "luxury" is factually necessary
in a specific context, such as describing a hotel category.

Environment: Windows, PowerShell. The repo root is the `wild-papagayo` folder. Its parent folder
holds unrelated projects and deploy snapshots that are NOT part of this repo.

## Source-of-truth rules

1. **Never hand-edit generated files** (`blog/`, `hotels/`, `tours/`, `private-tours/`, `categories/`,
   `profiles/`, `months/`, `destinations/`, `transfers/`, the generated finder/index pages,
   `sitemap.xml`, `rss.xml`, `llms.txt`, `*.min.css`, minified `*.js`). Edit the source or the
   template, regenerate, and review the diff. Hand edits are overwritten on the next run.
2. **Hotels have two data layers.** Edits land in `knowledge/master/hotels/`; `hotel-generator.ps1`
   reads the synced copy in `knowledge/hotels/`. Run `hotel-legacy-publish-all.ps1` before
   `hotel-generator.ps1` or pages silently render stale data. **`knowledge/hotels.json` (a single flat
   file, distinct from the `knowledge/hotels/` directory above) is a stale legacy artifact** (last
   substantively updated 2026-07-15, used only by `knowledge-validator.ps1`/`question-engine.ps1` for
   ID cross-checks) — never treat it as the authoritative hotel knowledge source; a 2026-09-29 audit
   used it by mistake and understated Wild Papagayo's real hotel/transfer-zone coverage as a result
   (see `seo-intelligence/reports/flamingo-all-inclusive-milestone-opportunity-analysis.md`).
3. **Edit `*.src.js` and `style.css`,** never the minified outputs.
4. **Template placeholders (`__NAME__`)** must have a matching replacement in the generator, and
   vice versa. Never remove one side without the other, or a literal token ships in pages.
5. **Internal links are extension-less** (`../tours`, `../hotels/andaz-costa-rica`). Files stay `.html`
   on disk and are served clean. New links in generators/templates must not end in `.html`.
6. **Content honesty:** do not invent prices, schedules, policies, hotel facts, reviews or
   testimonials. Testimonials may only reuse quotes already published on the homepage. Drive times
   should cite a real data source. Human factual review is required before publishing new articles.
7. Legacy "Tico Host" branding and assets were removed. Do not reintroduce them.

## Deployment safety rules (READ BEFORE TOUCHING ANYTHING)

- **NEVER deploy without an explicit instruction from the user in the current conversation.** Earlier
  approval, an allowlist entry, or a settings.json permission is not authorization.
- **`deploy-package.ps1` is not a dry run.** It regenerates *everything* in place (rewrites hundreds
  of files in the repo), deletes and recreates `..\wild-papagayo-deploy`, rewrites
  `..\wild-papagayo-deploy.zip`, and ends by running `indexnow-submit.ps1`, which **notifies search
  engines externally**. Treat running it as publish-adjacent; ask first.
- Production deploy is a separate manual step, run from the parent folder:
  `npx wrangler pages deploy "wild-papagayo-deploy" --project-name=wild-papagayo --branch=main --commit-dirty=true`.
  Never run it, or any `wrangler` command that writes to Cloudflare, unless the user says to.
- Only `wild-papagayo-deploy` (built by the script) is deployable. Sibling folders named
  `wild-papagayo-deploy-*`, `_verify*`, `_post_deploy_check`, `_tmp_*` and the `.zip` files are
  snapshots/scratch. Do not edit, deploy or delete them.
- The package excludes: `.git wild-cms engine knowledge questions reports node_modules docs templates
  seo-intelligence`, all `*.ps1`, `.env`, `script.src.js`, and non-public file extensions
  (`.md` files never ship). Keep it that way.
- **Cloudflare Pages Functions deploy rule (confirmed 2026-09-25, Bubu deploy):** when a `_worker.js`
  file exists at the deploy root, Cloudflare Pages uses that compiled bundle exclusively and does NOT
  process `functions/` directly. Any manual/surgical deploy that overlays only loose `functions/*.js`
  files (skipping `_worker.js`) will silently ship a STALE worker -- confirmed by a real staging
  incident where `functions/assistant.js`/`assistant-knowledge.json` were updated but the old
  `_worker.js` kept serving the previous knowledge. Any change under `functions/` requires rebuilding
  first: `npx wrangler pages functions build functions --outdir <tmp> --output-routes-path <tmp>/_routes.json`,
  then copying the resulting `_worker.js` and `_routes.json` into the deploy package. Never copy only
  `functions/` into a deploy folder that already has (or needs) a `_worker.js`.
- `deploy-package.ps1` aborts if `_worker.js` is missing, if `_routes.json` lacks `/assistant` and
  `/health`, or if the Bubu knowledge generator/validator fails. Never bypass those checks.
- To verify without publishing, run a single generator (for example `blog-generator.ps1`), then
  `content-link-validator.ps1`, and compare output to a baseline. Do not use the full package script.
- **Never trust a `wild-papagayo-deploy-*` folder as current production merely because of its name (added
  2026-09-29, after `wild-papagayo-deploy-current-baseline` was found stale — full record:
  `seo-intelligence/reports/deploy-baseline-repair-2026-09-29.md`).** Any such folder, including
  `current-baseline`, is a **point-in-time snapshot**, never a standing guarantee — nothing in this repository
  refreshes one automatically. Before building a deploy package from one: (1) find the most recent deployment
  recorded in `CURRENT-STATE.md`'s history; (2) compare it against the folder's own recorded deployment
  ID/date; (3) if the folder doesn't cover that deployment, refresh it first (copy from the actual last
  deployed package, or verify a sample of pages directly against `wildpapagayo.com`, normalizing the documented
  Cloudflare email-obfuscation/analytics injections — never treat those as real drift, but never wave away a
  substantive difference either); (4) only then build the next scoped overlay on top of it.
- **One-baseline model (established 2026-09-30, after a forensic audit found the scoped-overlay method had let
  `current-baseline` silently diverge from real production on dozens of files — full record: the "Production
  baseline rebuild" entry in `CURRENT-STATE.md`).** There is exactly one deploy folder now:
  `../wild-papagayo-deploy-current-baseline`, rebuilt directly from verified live production. **Never create
  another permanent task-named `wild-papagayo-deploy-<task>` folder** — build the next package in a *temporary*
  directory, deploy it, validate, refresh `current-baseline` from it, then delete the temporary directory.
  Historical task-named folders from before this date were moved (not deleted) to
  `../wild-papagayo-deploy-history-archive/` — that archive is for reference only, never a deploy source.
  **Cloudflare edge-normalization rules** (apply when comparing any local file to a live fetch, whether for a
  deploy check or a baseline rebuild): (1) `<span class="__cf_email__" data-cfemail="HEX">...</span>` — decode
  with a simple XOR cipher where the first hex byte is the key; (2) `href="/cdn-cgi/l/email-protection#HEX"` —
  same decode, reconstitute as `href="mailto:<email>"`; (3) the injected
  `<script data-cfasync="false" src="/cdn-cgi/scripts/.../email-decode.min.js"></script>` — strip entirely;
  (4) the injected Cloudflare Web Analytics beacon
  (`<script type="module" src="https://static.cloudflareinsights.com/beacon.min.js/..." ... data-cf-beacon=
  '...'></script>`) — strip entirely (this site does run Web Analytics; don't assume it's absent from a single
  spot-check that happened not to show it). None of these four are real content drift — a raw, unnormalized
  byte-size comparison against a live fetch will overstate differences and has produced false "drift" findings
  before. A stray inline whitespace/line-break collapse inside an HTML attribute has also been observed once
  (cosmetic, zero content change) — not worth a blanket normalization rule, but don't mistake it for real drift
  either.

## Google Search Console evidence rule

Google Search Console **is active** for `wildpapagayo.com`. There is no live GSC connector/API access
from this repository or the Codex research environment (`seo-intelligence/connectors/search-console-
client.ps1` checks for `GOOGLE_SEARCH_CONSOLE_CREDENTIALS_PATH` and will correctly report itself
unavailable) — that is a *connector* limitation, not evidence that the property doesn't exist or
isn't configured. Never collapse "the connector is unavailable" into "GSC is not configured."

Before stating that GSC evidence is unavailable for a research task:

1. Check `seo-intelligence/data/gsc/raw/` for the latest export, and read
   `seo-intelligence/data/gsc/manifest.json` first to see what's actually there.
2. Record the export date, reporting period, dataset type, and dimensions available for whatever you
   used.
3. Distinguish these conditions explicitly — do not collapse any of B-E into "GSC is not configured":
   - **A. NO_RELEVANT_EVIDENCE** — an export was checked but contains no relevant query/page match.
   - **B. DIMENSION_NOT_AVAILABLE** — GSC data exists but the needed dimension isn't in the export
     (e.g., the Generative AI Features export has no query-level or click data).
   - **C. PERIOD_NOT_COVERED** — GSC data exists but doesn't cover the needed dates.
   - **D. EXPORT_NOT_AVAILABLE** — no sufficiently current/raw export exists locally yet; ask the
     owner for one rather than substituting DataForSEO or inventing a number.
   - **E. CONNECTOR_NOT_AVAILABLE** — direct API access is unavailable, but local exports may exist
     (check `raw/` before concluding anything).

**Evidence priority for questions about Wild Papagayo's own Google performance:** GSC first-party
data (actual impressions, clicks, CTR, positions, queries, pages, countries, devices, and Google
Generative AI Features appearances Wild Papagayo already has) **before** DataForSEO. Use DataForSEO
for external market context instead — estimated search volume, who currently ranks, competitive SERP
landscape, keywords outside Wild Papagayo's current visibility. Do not substitute a DataForSEO
estimate for first-party GSC performance when GSC evidence is available, and do not substitute GSC
absence for "no opportunity exists" — a lack of GSC impressions for a brand-new topic doesn't
automatically mean there's no search opportunity, and GSC impressions alone don't automatically
justify a new article either. Treat standard Search performance and Google Search Generative AI
Features as separate datasets; never silently merge their metrics.

Research workflow order: existing-content audit -> GSC first-party evidence -> architecture/
cannibalization check -> external SERP research -> DataForSEO only if still needed -> decision.

## Research investment philosophy (SEO/SERP/AI intelligence)

Superseded (2026-09-24): the earlier posture of minimizing DataForSEO/API spend. Wild Papagayo is now
in an early growth/experimentation stage. **Minimizing spend is not the objective.** The objective is
useful information gain -> better decisions (SEO, content, architecture, conversion, competitive,
AI-discoverability, measurement). Full rationale, examples, and safeguards:
`seo-intelligence/reports/research-investment-policy.md`.

- **Every paid call still needs a decision question** it materially informs — that requirement is
  unchanged. What changed is that cost alone is never a reason to reject research with real
  information-gain; evaluate incremental value (what GSC/existing evidence/free research can't
  already answer), not just cheapness. A DEFER classification on a DataForSEO endpoint (per
  `seo-intelligence/data/processed/dataforseo-endpoint-decision-matrix-v1.json` and future updates)
  means *not justified yet*, never *permanently excluded* — re-evaluate when a real decision question
  makes it valuable, including endpoints costing materially more than the cheapest alternative.
- **A hard cost cap is cost *control*, not cost *avoidance*.** It exists to catch accidental
  expansion/runaway loops/duplicate calls, not to enforce a minimum-spend habit. A cap breach means
  stop and explain the gap; it does not mean every experiment must target the cap's floor. Prefer a
  small pilot when the open question is "is this data source useful at all," over either an outright
  refusal or a full-scale commitment.
- **Present material paid research for authorization** with: decision question, what's already known,
  what's unknown, proposed source, expected information gain, how the result could change action,
  estimated cost, proposed hard cap, and a recommendation (RUN/PILOT/DEFER/NOT_NEEDED) — the owner
  decides, this is a proposal format, not a pre-authorization.
- **Unchanged, still permanent:** GSC remains the first-party truth for Wild Papagayo's own Google
  performance ("what is happening to us"); DataForSEO/AI intelligence answer "what is happening
  around us" and never substitute for first-party performance data. More keyword/competitor/AI data
  must never translate automatically into more pages — the existing-content audit ->
  cannibalization-check -> decision sequence (see the GSC evidence rule above) still gates every
  content outcome. Facebook remains a real discovery signal but is one input among several (GSC,
  DataForSEO, SERP/AI monitoring, competitor/citation analysis). Cost logging (endpoint, task count,
  expected/actual cost, decision question, date, result) remains mandatory for every paid call. Still
  prohibited regardless of this policy: research with no decision question, giant keyword dumps,
  repeated identical calls, automatic every-market/every-device duplication, running an endpoint
  because it exists, and any paid execution without explicit authorization in the current session.
- **UNKNOWN_COST guard (added 2026-09-28):** an unknown endpoint price is never a verified cost estimate.
  Without a price from Wild Papagayo cost history, official pricing already held locally, or a verified
  previous call, classify the next call `UNKNOWN_COST` and do not execute it where it could violate the
  remaining hard-cap budget. Never enforce a hard cap with a guessed price. (Origin: a guessed $0.04 guard
  let a $0.18 clickstream call through; the pilot spent $0.23268 against a $0.15 hard stop.)

## DataForSEO methodology update (2026-09-28, corrected by the live pilot)

Extends, never replaces, the two sections above. Full text and evidence labels
(VENDOR_GUIDANCE / LIVE_API_VALIDATED / WILD_PAPAGAYO_PILOT_OBSERVATION / INFERENCE / NOT_VALIDATED):
`seo-intelligence/reports/dataforseo-methodology-update-2026-09-28.md`. Pilot evidence:
`seo-intelligence/reports/dataforseo-methodology-validation-pilot-2026-09-28.md` (8 keywords, one transfer
cluster, US/English: treat its observations as a small sample, not general rules).

- **Ownership is multi-signal, never a fixed sequence.** Weigh together: traveler intent, entity/geographic
  meaning, route direction, existing content owner, GSC, core keyword, Search Intent, SERP URL overlap, SERP
  domain overlap, information gain, cannibalization risk, commercial relevance. No single signal decides;
  volume alone never decides. Explicit semantic differences (e.g. opposite route direction) are never erased
  by a shared core keyword.
- **Core keyword = LEXICAL_CLUSTER_SIGNAL**, supporting evidence only (`keyword_properties.core_keyword`).
  The pilot saw it group word order, inflection and opposite travel directions, but not
  shuttle/transportation/transfer; it never overrides intent, direction, entity meaning, architecture, GSC or SERPs.
- **Search Intent = SECONDARY_INTENT_SIGNAL** (`keyword_intent{label,probability}` +
  `secondary_keyword_intents[]`). Noisy in the pilot; it never independently decides NEW PAGE, MERGE, OWNER,
  DELETE or CANNIBALIZATION. Manual intent classification stays primary.
- **Zero or null measurable volume != proof of zero demand.** Keep NUMERIC_ZERO, NULL/NO_MEASURABLE_DATA and
  NON_ZERO distinct when raw evidence allows (the pilot's long tails were Google Ads `null`, not 0). Weigh parent
  demand, intent, 12-month parent trend, SERP behavior, GSC, first-party traveler evidence, Facebook/community
  signals and existing ownership.
- **Clickstream: KEEP_NOT_NEEDED**, outside the routine workflow (the pilot found no gain for null long tails;
  the dedicated endpoint billed $0.18 for 3 keywords). Revisit only for a clearly bounded use case.
- **SERP overlap** is self-computed: store URL_OVERLAP and DOMAIN_OVERLAP separately, with the formula. URL
  overlap is the stricter page-level signal; domain overlap is contextual (broad domains such as reddit,
  rome2rio, facebook, tripadvisor inflate it). The ~60%/30% domain bands are VENDOR/INDUSTRY CALIBRATION, NOT YET
  VALIDATED FOR WILD PAPAGAYO; never automated ownership rules.
- **Endpoint matrix:** Keyword Suggestions and Search Intent are CONDITIONAL (use only for a specific decision).
- **AI metrics stay separate:** MENTION, CITATION, AI OVERVIEW PRESENCE, AI OVERVIEW CITATION,
  RECOMMENDATION. No composite AI score. Recommendation is not a native metric; if measured, define it on a
  fixed prompt set and label it SAMPLE_BASED.
- **Never mix LLM methods on one trend line:** LLM Mentions (aggregated database), LLM Responses (on-demand
  generation on exact prompts), LLM Scraper (ChatGPT Search retrieval). Label the method on every record.
- **Organic Top 10 is not required for AIO citation** (vendor guidance, not yet validated here). Future high-value SERP snapshots should store organic
  rank/URLs/domains and AIO presence/citations/WP citation position separately.
- **Async AIO is selective:** it raises task cost; use only on the high-value core watchlist, not discovery.
- **Monitoring target (proposal, nothing active):** Tier 1 US/English core commercial weekly (Standard
  workflow, advanced response, ~Top 10, selective async AIO); Tier 2 Costa Rica/Spanish monthly; Tier 3
  discovery monthly via Ranked Keywords/SERP Competitors; Tier 4 opportunity research on demand only.
- **Three competitor universes, never merged:** organic SERP, local/Maps, AI-answer.
- **Facebook zero- or null-volume questions** are neither NO ACTION nor NEW ARTICLE by default: traveler
  signal -> existing owner -> GSC -> existing research -> the multi-signal ownership check above ->
  architecture/cannibalization -> information gain -> commercial/geographic relevance -> decision (NEW OWNER / UPDATE / ADD SECTION / ADD FAQ / INTERNAL LINK / MERGE / CHILD CONTENT /
  DEFER / NO ACTION). Facebook stays a discovery engine, not a publishing queue.
- **Before any paid request** state KNOWN, UNKNOWN, WHAT_THIS_RESEARCH_ADDS, WHAT_DECISION_IT_COULD_CHANGE
  (same fields as the research proposal format). GSC-first rule unchanged.

## Rendered-layout verification rule (visual claims need visual evidence)

Added 2026-09-24 after `EXP-001-RINCON-COMMERCIAL-CLARITY`'s diagnosis (pricing "buried late in the
page") was found factually wrong once the page was actually rendered — the site's shared tour template
places a dedicated `__PRICE_TEASER__` block (a "From $X" price + CTA) early on every tour page, and
CSS (`.tour-summary-card { order: 1; }` plus responsive column rules) reorders the full pricing card
ahead of source order on both mobile and desktop. The diagnosis had been built entirely from raw HTML
source order.

**Rule**: any conclusion involving prominence, above-the-fold placement, visual order, CTA visibility,
pricing visibility, sidebar placement, sticky elements, mobile vs. desktop ordering, hidden/collapsed
content, or visual hierarchy **must not** be based solely on raw HTML source order, source-file order,
DOM order without computed CSS, text extraction, or static scraper output. Before labeling something a
UX/conversion/presentation gap, verify the actual rendered layout at relevant viewport(s) — for a
responsive commercial page, at minimum mobile (e.g. 390px) and desktop (e.g. 1280px); use more than one
mobile width when layout behavior could plausibly differ between them. A working method already
proven on this project: headless Chrome/Edge (`chrome.exe --headless=new --disable-gpu --window-size=W,H
--screenshot=path.png <url>` against the live production URL), reviewed as an image. If rendered
verification genuinely isn't available, state the conclusion as `RENDERED_LAYOUT_NOT_VERIFIED`, not as
settled fact.

**Scope discipline — do not overapply this.** Rendered verification is required only when the
conclusion depends materially on visual position or presentation (examples: "pricing is buried," "CTA
is below the fold," "FAQ appears before pricing," "sidebar isn't prominent," "mobile users see X after
Y"). It is not required for canonical checks, JSON-LD inspection, meta/title verification, internal
link existence, wording analysis, schema synchronization, or URL status checks — those remain
text/data-level checks as before.
